# Plan, August 2026

Packaging, two testing workstreams, a firmware development loop, a
documentation site, and a protocol study. Written to be worked through in waves,
with the decisions that gate other work taken first.

Progress and blockers are recorded **in this file** as they happen, so that the
next person to pick it up reads why something was skipped rather than
rediscovering it.

## Wave 1 — the two decisions everything rests on

### A. Headless

MeshBench is a desktop application that needs a display and a GPU path, and both
testing workstreams want to run through the GUI *and* in CI. MeshCore ships a
`.devcontainer`, so firmware developers will hit the same wall.

Two options: drive the real binary under Xvfb with software GL, or add a genuine
headless mode sharing the control-socket verbs. Spike both, pick one, write the
ADR. Blocks the harnesses in Wave 3.

**Status: decided, ADR-0019.** A headless mode, and not because Xvfb failed.
Xvfb offers GLX with Mesa direct rendering, and the application starts under it
and binds its control socket - but no verb answered. Control verbs are serviced
on the frame thread, so a harness driving them is hostage to the renderer, and a
virtual display hides that coupling rather than removing it. The spike script is
kept at `tools/headless/xvfb-spike.sh`; why verbs do not answer under Xvfb was
not isolated, and that is recorded rather than glossed.

### B. Tool manifest

One contract for which tools, which versions, and where they live, consumed by
packaging and both harnesses. The search order already exists — environment
variable, then beside the binary, then `~/.cache/meshcoresim/tools`, then PATH —
so this pins versions and provenance rather than inventing a mechanism.

**Status: written, `docs/tools-manifest.md`.** Four tools, why each is pinned
rather than taken from a distribution, and what a released bundle ships. QEMU
must be symlinked rather than copied, because it resolves its own path to find
its data files.

## Wave 2 — three parallel tracks

### C. Fork release CI

**Status: QEMU done.** `MeshBench/qemu` builds `qemu-system-xtensa` in CI and
packages it, Linux only, with macOS and Windows as visible skipped rows carrying
their reasons. It asserts `hw/ssi/sx1262.c` is in the tree it built, because a
checkout that resolved to upstream would produce a QEMU that runs and reports no
chip present. `radioserver` is not in CI yet.

| dependency | state | work |
|---|---|---|
| `radioserver` | 40 KB, C++17 | build in CI; **keep the TCP path** even though Linux does not need it, because Windows will |
| QEMU fork | built by hand on one machine | CI from scratch. `--enable-gcrypt` or the `esp32` machine will not instantiate |
| Renode fork | CI, portable, runtime bundled | done |

Linux only. macOS and Windows get **skipped matrix rows with the reason in the
file** rather than absence, because an absent row is forgotten and a skipped one
with `# no runner yet` is picked up.

### D. Linux packaging

**Status: workflow written**, `.github/workflows/package.yml`. Built on the
oldest Ubuntu we support, bundles both emulators beside the binary, symlinks
QEMU because it resolves its own path to find its data files. Not yet run.

AppImage or a tarball built on the oldest base we are willing to support — glibc
is most of what "every flavour of Linux" means. A Nix flake is cheap and fits,
given MeshCore ships `default.nix` and `.envrc`.

`docs/packaging-emulation.md` gains a "what is not built yet" section.

### E. Shipped mesh fixtures

**Status: small done, `docs/fixtures.md`.** Fife, 55 nodes, from live CoreScope
with regions inferred from 20,500 packets and applied to 53 of them, in strict
and permissive variants. Medium and large are the same recipe with different
boundaries.

Two gaps found while building it, both in the control socket rather than the
model: `nodes.place` refuses room-server and emitter, and `firmware.set` with a
role and no node converts every node to that role rather than pinning one.

Built from live CoreScope at
<https://scotmesh-corescope.mm7roq.compute.oarc.uk/>, in the order that works:

    boundary.set → boundary.accept (once per region; the chosen set unions)
    import.set_source → import.fetch → import.commit strategy "replace-all"
    firmware per role
    infer.run {hours: 168} → poll infer.result → infer.apply
    verify

**Bake the result, not the recipe.** A fixture must load with no network and no
re-inference, so it stores the applied per-node regions and default scope. Its
provenance records the snapshot date, holder counts per scope, node counts, and
how many nodes were dropped for null-island or missing positions.

| fixture | boundary | scope |
|---|---|---|
| small | Fife | `#fif` |
| medium | Scotland | `#sco` |
| large | Scotland + Ireland | `#sco` + `#ioi` |

Scopes are written **`#`-prefixed**. The key on the wire is
`sha256("#sco")[:16]` while the repeater CLI takes it bare, and getting this
wrong means every node transmits, nothing relays, and nothing reports an error.

Composition: at least two companions, deliberately spread rather than wherever
CoreScope happens to cluster them, and one of every node kind that exists —
simple repeater, advanced repeater, companion, room server, SDR observer,
emitter. **There is no sensor kind and this plan does not add one**; the
provenance says a sensor node is absent so a reader is not left wondering.

Two variants of each, both shipped:

- **permissive** — the real inferred regions *plus* unscoped flooding, so a
  first run works without anyone setting a scope
- **strict** — the real regions only

The permissive variant says so in its provenance and in the UI, with one
documented line to restore strict. A fixture that quietly forwards what the real
network drops would produce exactly the flattering-but-wrong answer this
simulator exists to avoid.

Firmware pinned per role: `repeater-v1.17.0`, `room-server-v1.17.0`. A bare
`v1.17.0` resolves nothing and reports "no native builds published", which points
at the release rather than at the string.

### H. meshbench-docs

**Status: repository created, private, Pages not enabled.** First view written
from a real window-only capture, with the annotation tool and the rule that
keeps it true. The first capture attempt took the whole desktop including a
browser showing MeshCIM, which is why the rule says window-only and look before
committing.

New **private** repository, GitHub Pages, unpublished. Unblocked: screenshots
come from the running application, not from a packaged build.

- capture with `spectacle --new-instance -b -n -f -o` — the plain form
  core-dumps on this machine
- drive the app to a known state through control-socket verbs, capture, then
  **annotate with red circles** for step-by-step instructions
- **diagrams in the report style**: the stack figures with a REAL/SIMULATED
  gutter and a boundary line, generated programmatically so alignment is exact
- every view documented, plus how it works, how to test with it, how to
  experiment with it
- a Claude rule with a **trigger** — a change under `internal/ui/` requires a
  docs check — rather than an instruction to keep it updated

## Wave 3 — the harnesses

### F. App-developer testing

**New panel: Companion bench.** The Packet timeline is mesh and RF level; an
application developer does not care about capture effect. They need the
companion protocol decoded in both directions — contacts, channels, messages,
acks — a pasteable endpoint (PTY path or host:port), fault injection with
buttons, and one click for "give me a mesh and an endpoint".

Alongside it: assertions, JUnit output, exit codes. MeshCIM is the test subject,
cloned locally and **never pushed anywhere**.

CI-gating scenarios are **native only**. Emulated nodes run on wall time and two
runs of one seed will not match.

### G. Firmware development loop

MeshCore developers live in PlatformIO, so meet them there:

- **`post:meshbench.py`**, a PlatformIO extra_script handing the freshly built
  artefact to MeshBench over the control socket. Idiomatic beside their existing
  `merge-bin.py`, `create-uf2.py` and `arch/stm32/build_hex.py`.
- **`post:meshbench.py` is written**, `tools/platformio/`. Reads the board and
  role from the environment name and hands the image to a running workbench
  through `firmware.import`. Verified by driving the same verb with a real image.
- **`msim firmware use <path>`** and a watch mode, so any editor can bind it. A
  task snippet beats an extension: cheaper, and it works today.
- **A/B defaulting to working tree against a pinned upstream tag**, which is the
  literal shape of their pull requests — fork from `dev`, branch `fix/…`.
- the **±20% measurement floor** at around eight simultaneous senders baked in:
  a control arm and enough seeds, or the delta is noise.

## Wave 4 — the protocol study

Last, and the priority deliverable.

**Read before proposing.** MeshCore at a pinned tag: `examples/simple_repeater`,
`examples/companion_radio`, `Mesh.cpp`, `Dispatcher.cpp`. Ideas come from the
code. The previous study found that `allowPacketForward()` only ever returns
false, and that the loop thresholds are indexed by path-hash size so all three
settings are *identical by construction* at three bytes — arms that vary nothing
are worth knowing about before spending a day on them.

**Eight candidates**, each stated as mechanism, hypothesis, the metric that would
show it, and the cost it adds. Each on its own **local** branch of a local
MeshCore clone; nothing is pushed.

**Pre-register** metrics, seeds and arms before running, so the result is not
fished out afterwards.

**Design that survives scrutiny:**

- a **control arm the firmware guarantees is identical**. If it differs from
  itself, the harness has a reproducibility problem, and the study stops there
  and says so.
- medium fixture, native, many seeds for the headline; large only for claims
  about scale
- the ±20% floor quoted beside every delta

Report in the style of the listen-before-talk one: figures comparing the things
that matter, honest limits, no em-dashes.

## Standing constraints

- **Never push MeshCIM anywhere.** It is owned by PaulMcGinley, private, with a
  proprietary licence. Working on it locally is fine.
- **Never push the local MeshCore branches.**
- **Every simulation run in this plan is native.** Not only the CI-gating ones:
  emulated nodes run on wall time, so two runs of one seed do not match, and
  they cost about a core and 150 MB each. Emulation is a conformance tool - does
  this published build come up and talk - and nothing in this plan needs it.
- If an emulated node is ever run: eight saturate a twelve-core machine, and past
  the ceiling nothing reports an error. Boots stretch and simulated time falls
  behind the wall clock, which reads as a mesh gone quiet.
- Keep main green: build, `gofmt`, `go vet`, `go test` before every merge, and
  read your own diff for dead code and files over 500 lines before opening a PR.
